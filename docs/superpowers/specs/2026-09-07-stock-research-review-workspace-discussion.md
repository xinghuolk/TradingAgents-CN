## 1. 背景

TradingAgents-CN 已经覆盖股票筛选、自选、个股行情、多智能体分析、分析报告、模拟交易，以及真实券商持仓和成交导入。`../stock` 则补充了个人投资流程中更偏长期积累的能力，包括个股笔记、研究纪律、决策记录和复盘思路。

两者服务同一位用户、同一批证券和同一条工作流，不应继续建设为两个独立产品。后续应以 TradingAgents-CN 为唯一产品入口，将有价值的概念融入现有数据、API 和页面体系，而不是直接移植 `../stock` 的 Markdown 文件、SQLite 索引或独立定时器。

目标工作流为：

```text
筛选 / 自选
  -> AI 分析与人工调研
  -> 个股笔记与当前投资论点
  -> 人工决策快照
  -> 模拟执行或真实成交导入
  -> 持仓跟踪
  -> 复盘
```

## 2. 当前优先级

当前优先建设：

1. 个股笔记。
2. 个股调研与长期投资论点。
3. 人工决策快照。
4. 结合分析、决策、成交和持仓的复盘。

每日定时更新行情仍然需要建设，但不作为本阶段的首要产品功能。它是后续自动生成持仓摘要、计算阶段表现和提供复盘提醒的数据基础，应在研究与复盘核心流程明确后单独设计。

## 3. 已确认的产品边界

### 3.1 使用场景

- 产品主要供个人使用。
- 以提醒、建议和可追溯性为主，不设置严格审批和过多门禁。
- 缺少非关键字段或关联记录时，应尽量允许保存并显示提示。
- 模拟账户与真实券商账户必须分别呈现，不合并持仓和收益。
- 导入真实成交用于持仓跟踪和复盘，不扩展自动下单或券商交易连接。

### 3.2 AI 与人工决策边界

- AI 的 `final_trade_decision` 只能称为分析建议或决策草稿。
- AI 内容不能自动成为用户批准的正式决策或正式复盘。
- AI 可以基于已有研究、笔记、成交和行情生成复盘草稿。
- 用户编辑并确认后，内容才成为正式记录。
- 保留原始 AI 草稿、人工确认版本、确认时间和后续修订历史。
- 不建设 AI 模型效果评估，不统计模型排名、建议命中率、收益归因或人工修改幅度等聚合指标。

### 3.3 AI 来源信息

所有 AI 产物统一记录来源元数据，包括：

- 服务商。
- 模型名称。
- 思考级别，例如 `low`、`medium`、`high`。
- 生成时间。
- 来源分析报告或任务标识。
- 提示词或生成模板版本。

这里只记录调用配置和来源，不保存模型内部思维过程。

### 3.4 内容与附件

- 内容编辑以自由 Markdown 为主。
- 日期、标签、记录类型、关联决策、失效条件和引用关系等少量信息结构化保存。
- 第一版支持外部链接和站内分析报告引用。
- 第一版不新增 PDF、图片等附件上传与存储。

## 4. 已确认的信息架构

### 4.1 保留现有个股详情

现有 `/stocks/:code` 继续作为行情详情页，负责：

- 股票代码、名称和市场。
- 最新行情与数据时间。
- K 线。
- 新闻和公告。
- 基础资料。
- 最近 AI 分析摘要及完整报告入口。
- 真实持仓和模拟交易快捷入口。

该页面已经承担较多行情和分析展示职责，不继续堆叠完整的长期写作、决策和复盘界面。

### 4.2 新增个股研究工作区

新增 `/research/:code`，作为某只股票的长期研究工作区。初步包含：

- 当前论点：维护最新投资论点、关键假设、风险、失效条件和待确认问题。
- 笔记：按时间记录自由 Markdown 笔记、标签和外部链接。
- 调研：组织人工调研内容，并引用已有 AI 分析报告。
- 决策：保存买入、加仓、减仓、卖出或继续观察时的人工决策快照。
- 复盘：对照历史论点、决策、成交、持仓变化和后续事实进行回顾。

个股详情和研究工作区共享同一标准证券标识和基础数据，不重复建立股票档案。两边提供互相跳转入口。

### 4.3 新增全局研究与复盘中心

新增 `/research`，用于跨股票查看：

- 最近编辑的研究工作区。
- 最近笔记和调研记录。
- 待确认问题。
- 系统建议复盘的事项。

该页面是个人工作清单，不设置逾期处罚、强制完成或审批状态。真实持仓、成交记录和分析报告可以跳转到对应股票的研究工作区。

## 5. 已确认的数据设计方向

数据统一存入 TradingAgents-CN 当前使用的 MongoDB，不沿用 `../stock` 的 Markdown 文件加 SQLite 存储。

### 5.1 `stock_research_workspaces`

每位用户、每只标准证券至多一个当前工作区，保存：

- 标准证券标识，包括市场和代码。
- 当前投资论点。
- 关键假设。
- 主要风险。
- 失效条件。
- 待确认问题。
- 最近更新时间和当前版本信息。

### 5.2 `stock_research_entries`

保存统一时间线记录，记录类型至少包括：

- `note`：一般笔记。
- `research`：调研记录。
- `decision`：人工决策快照。
- `review`：正式复盘或尚未确认的复盘草稿。

通用字段包括 Markdown 内容、标签、外部链接、创建时间、更新时间和来源。记录可以关联：

- 站内分析报告。
- 人工决策。
- 真实成交。
- 模拟成交。
- 某日真实持仓快照。

不同类型可以增加少量专用结构化字段。除证券标识和基本内容外，关联缺失原则上只提示，不阻止保存。

### 5.3 `stock_research_revisions`

保存工作区和时间线记录的历史版本，用于还原“当时掌握了什么、当时如何判断”，避免后来的观点覆盖历史内容。

### 5.4 AI 元数据建议结构

所有 AI 产物使用统一字段，而不是各功能自行定义模型信息：

```yaml
ai_provenance:
  provider: string
  model_name: string
  reasoning_effort: string | null
  generated_at: datetime
  source_report_id: string | null
  source_task_id: string | null
  prompt_version: string | null
```

AI 草稿记录还需要区分原始生成内容与用户确认后的正式内容。

## 6. 已确认的内容行为

### 6.1 当前研究页与时间线

内容分为两层：

- 当前研究页可持续编辑，用于维护最新的投资论点和研究结论，并保留版本历史。
- 时间线记录以追加为主，可修正文案，但必须保留原始版本、修改时间和修订历史。

### 6.2 决策快照

当用户记录买入、加仓、减仓、卖出或继续观察时，从当前研究页保存一份只读语义的快照，至少保留当时的论点、关键假设、风险、失效条件和计划。

该功能不是审批流程，不阻止真实交易，也不要求每笔真实成交必须事先存在决策。未关联决策的成交可以在复盘中标记为计划外交易。

### 6.3 复盘模板

复盘采用轻量模板，并允许自由增删内容。建议覆盖：

- 原判断是什么。
- 哪些事实得到验证或被证伪。
- 股价与基本面发生了什么变化。
- 实际操作是否符合当时计划。
- 偏差主要来自信息、逻辑、时机还是执行。
- 当前论点是否继续有效。
- 下一步观察事项。

用户可以随时从个股研究工作区创建复盘。系统未来可以根据持仓变化、成交导入和时间间隔提供建议复盘提醒，但不强制完成。

## 7. 与现有系统的衔接

### 7.1 分析报告

现有 `analysis_reports` 和 `analysis_tasks` 继续作为 AI 分析事实来源。研究记录只保存稳定引用和必要的展示快照，不复制整份报告。

现有报告已经包含 `model_info` 和节点级 `model_usage`。新设计需要在此基础上统一服务商、模型名称和思考级别的记录方式，并兼容旧报告缺少部分字段的情况。

### 7.2 真实持仓与成交

现有真实持仓导入集合继续作为券商事实来源。研究记录通过稳定标识关联真实成交和持仓日期，不修改券商导入事实。

真实成交与决策的关联属于用户解释层，可以后补、修改或取消。不得为了建立关联而改写原始导入记录。

### 7.3 模拟账户

模拟成交可以被研究和复盘引用，但必须明确显示为模拟数据。所有 API、页面标签和复盘上下文均需保留账户类型，禁止与真实账户混算。

### 7.4 行情数据

复盘可以引用现有行情数据。行情缺失或过期时显示数据日期和警告，不阻止用户写笔记或完成复盘。

每日行情自动更新应复用 TradingAgents-CN 已有调度和任务基础设施，不移植 `../stock/src/stock/market_data/timer.py` 形成第二套调度系统。

## 8. 明确不在当前范围内

- 自动下单或真实券商交易连接。
- 合并真实账户与模拟账户收益。
- 强制审批、严格研究门禁或强制复盘完成率。
- AI 模型效果排名和收益归因。
- PDF、图片及其他附件上传。
- 直接移植 `../stock` 的 SQLite、Markdown 文件存储或独立定时器。
- 在当前讨论完成前编写实施代码。

## 9. 后续需要讨论并确认

以下内容尚未最终确定，应按顺序继续讨论：

1. 个股研究工作区的页面布局、页签关系和默认首页。
2. 当前论点、普通笔记和调研记录各自的具体编辑体验。
3. 决策快照的最小字段、创建入口以及与成交的手工关联方式。
4. 复盘草稿的生成入口、AI 上下文范围和人工确认流程。
5. “建议复盘”的触发规则，例如发生新成交、持仓变化、论点长期未更新或用户主动设置日期。
6. 全局研究与复盘中心的列表、筛选、搜索和提醒呈现。
7. 删除、归档、恢复和版本查看行为。
8. API 边界、MongoDB 索引、并发更新及旧数据兼容策略。
9. 从 `../stock` 复用哪些模板和业务概念，以及是否需要迁移已有个人笔记或决策记录。
10. 每日行情更新的市场范围、执行时间、关注股票集合、失败重试和手动补跑方式。
11. 测试范围、验收标准和分阶段交付顺序。

## 10. 建议的后续设计顺序

1. 先完成页面与核心操作流程设计。
2. 再确定数据字段、API 和版本策略。
3. 单独设计 AI 复盘草稿的上下文与来源追踪。
4. 单独设计轻量复盘提醒。
5. 形成最终设计文档并由用户确认。
6. 最终设计确认后再编写实施计划。
7. 研究与复盘核心能力落地后，再设计每日行情自动更新。
